# System Architecture

Caracal Tech Motors is a pnpm/Turbo monorepo with a Next.js frontend, an Express API, shared TypeScript packages, and Prisma-backed PostgreSQL persistence. This document reflects the current stabilized runtime and backend implementation.

## Repository Layout

```text
apps/
  api/                 Express API runtime, routes, Prisma schema, migrations
  web/                 Next.js application
packages/
  @caracal/auth/       Shared auth utilities
  @caracal/config/     Shared config helpers
  @caracal/db/         Prisma client lifecycle helpers
  @caracal/types/      Shared TypeScript types
  @caracal/utils/      Shared utility functions
docs/                  Supporting backend and local development notes
scripts/               Local setup and startup scripts
docker/                Local infrastructure helpers
```

## Runtime Model

The root workspace is managed by pnpm and Turbo:

- `pnpm install` resolves all workspace dependencies.
- `pnpm dev` starts the configured app development tasks through Turbo.
- `pnpm build`, `pnpm lint`, and `pnpm type-check` run the corresponding workspace pipelines.
- `pnpm db:*` commands delegate database work to the API workspace.

The default local ports are:

- Web: `http://localhost:3000`
- API: `http://localhost:3001`
- API health: `http://localhost:3001/health`

## Application Boundaries

### Web Application

`apps/web` contains the Next.js frontend. The frontend consumes the API through the configured public API URL and remains separately owned from backend runtime stabilization work.

### API Application

`apps/api` is an Express service responsible for public intake flows and backend persistence. The API mounts:

- `GET /` for structured service status.
- `GET /health` for simple health checks.
- `POST /api/bin-uploads` for secure BIN file uploads.
- `POST /api/quote-requests` for quote intake.
- `POST /api/product-inquiries` for product inquiry intake.
- `POST /api/workshop-consultations` for workshop consultation leads.

The API uses:

- Helmet for baseline HTTP security headers.
- CORS with `CORS_ORIGINS`.
- Request context middleware for request IDs.
- Pino request logging.
- JSON body parsing with a 1 MB limit.
- Zod validation middleware for JSON intake payloads.
- Multer memory storage for `.bin` upload validation before persistence.
- Centralized structured success and error responses.
- Centralized async route error handling.

## Data Layer

Prisma is owned by `apps/api`:

```text
apps/api/prisma/schema.prisma
apps/api/prisma/migrations/
apps/api/prisma/seeds/
```

The generated Prisma client is consumed through `packages/@caracal/db`, which exposes a singleton client lifecycle:

- `getPrismaClient()`
- `disconnectPrismaClient()`
- `getDatabaseStatus()`

The current backend models are:

- `User`
- `BinUpload`
- `QuoteRequest`
- `ProductInquiry`
- `WorkshopConsultationLead`
- `AuditLog`

The backend intake models use indexed lookup fields for operational review, including email, status, SKU, upload hash, quote linkage, request ID, action, entity, and creation time.

## Backend Feature Flow

### Quote Requests

Quote requests are validated, persisted with a generated `QR-*` reference code, and written to the audit log after successful creation.

### Product Inquiries

Product inquiries are validated, persisted with a generated `PI-*` reference code, and written to the audit log after successful creation.

### Workshop Consultation Leads

Workshop leads are validated, persisted with a generated `WC-*` reference code, and written to the audit log after successful creation.

### BIN Uploads

BIN uploads use multipart form data. The backend:

- Accepts a single `file` field.
- Requires a `.bin` extension.
- Allows binary MIME types only.
- Enforces `BIN_UPLOAD_MAX_SIZE`.
- Rejects empty uploads.
- Computes SHA-256 for stored content.
- Sanitizes the original filename.
- Stores object data through the storage abstraction.
- Persists upload metadata in `BinUpload`.
- Optionally links to an existing `QuoteRequest`.
- Writes an audit log after successful creation.

## Storage

Storage is abstracted behind `apps/api/src/lib/storage.ts`.

Local development stores uploads under `LOCAL_UPLOAD_DIR` or `uploads` by default. When all Cloudflare R2 variables are configured, the same storage path writes through the S3-compatible R2 client:

- `R2_ENDPOINT`
- `R2_REGION`
- `R2_BUCKET`
- `R2_ACCESS_KEY_ID`
- `R2_SECRET_ACCESS_KEY`

Object keys are generated by the API and use date-based BIN upload prefixes.

## Security And Operations

The API currently includes:

- General API rate limiting through `RATE_LIMIT_MAX_REQUESTS`.
- Intake submission rate limiting through `INTAKE_RATE_LIMIT_MAX`.
- Upload rate limiting through `UPLOAD_RATE_LIMIT_MAX`.
- Request IDs on structured responses.
- Structured logs through Pino.
- Audit rows for successful intake and upload writes.
- File type, file count, file size, and file emptiness checks for uploads.
- `trust proxy` enabled for reverse proxy deployments such as Cloudflare.

Sensitive runtime values are configured through environment variables and documented in `.env.example`.

## Development Workflow

Fresh clone target:

```bash
git clone <repo-url>
pnpm install
pnpm dev
```

Before pushing backend runtime changes, run:

```bash
pnpm --filter @caracal/api prisma:generate
pnpm lint
pnpm type-check
pnpm build
```

For database-backed local development:

```bash
docker compose up -d postgres
pnpm db:migrate
pnpm dev
```

## Current Boundaries

This architecture keeps frontend presentation, API runtime behavior, shared package contracts, and persistence concerns separate. Backend stabilization work should stay inside API, shared backend packages, Prisma, runtime docs, and repository-level tooling unless a task explicitly calls for frontend changes.
